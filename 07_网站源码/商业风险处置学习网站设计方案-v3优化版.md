# 商业风险处置学习网站设计方案（v3 优化版）

> **版本说明**：v3 基于 v2 定稿 + 现有站点 data.js 现状诊断，重点补强六方面：量化验收指标、多文件数据架构、内容编写规范、试跑验证机制、学习质量闭环、核心页面线框描述。新增/修订内容以 `▶` 标记。

---

## 摘要

本方案为「商业风险处置实战系列学习站」的设计定稿，回答「建什么、怎么建、按什么标准验收」三个问题。

**建设对象**：以工作区 19 份风险处置内容资产为底座，构建一个覆盖知识沉淀、知识库、知识学习三大方向的纯静态学习网站。

**核心设计**：六大栏目（学习路径 / 理论课堂 / 实操工具箱 / 沙盘训练 / 案例库 / 法规参考）+ 13 周成才路径 + 约 80 篇结构化文章 + 五阶段建设路线（P0 内容标准化 → P0.5 试跑验证 → P1 内容全量入站 → P2 学习闭环 → P3 训练站升级）。

**关键技术决策**：延续纯静态架构，**▶ 数据层按栏目分拆为多文件**（data-theory.js / data-tools.js / data-lab.js / data-cases.js / data-law.js），解决单文件 80 篇文章的体积与维护瓶颈；data.js 退化为索引调度文件。

**▶ 验收主线**：每阶段有可验证的站内成果 + 可量化 KPI，以「看得懂理论、拿得到工具、练得出技能」为总验收标准。

**设计依据**：2026-09-14 内容盘点（18 份资产）；《商业风险处置顾问》职业画像素材（2026-09-17）；现有站点 data.js 现状诊断（30 条目，多条标题截断、正文缺失）；本方案与其保持一致口径，作为实施契约。

## 1 项目概述

### 1.1 现状分析与建设背景

商业风险处置（企业风险识别、定级、止损、处置、复盘）是一个高度依赖「方法论 + 工具 + 实战经验」的领域，但目前从业者面临三个普遍问题：资料零散不成体系、学了无法立刻用于业务、缺少可验证的训练场景。

工作区已积累 19 份风险处置内容资产，覆盖「认知理论 → 学习规划 → 实操模板 → 评估测算 → 法规参考 → 岗位方法论」的完整学习价值链。**▶ 现有站点雏形已搭建四文件骨架（index.html + app.js + data.js + style.css），data.js 已录入约 30 条目，但存在以下具体问题：**

| 序号 | 问题 | 影响 | 解决章节 |
|------|------|------|----------|
| 1 | 19 份资产仅 2 份接入（学习计划 + 白皮书），17 份缺席 | 内容覆盖残缺 | 第 4 章 |
| 2 | data.js 多条标题为截断半句（如 whitepaper-3「第三，将风控等同于事后补救手段…」） | 导航不可用 | 第 5 章 |
| 3 | 部分正文严重缺失（如 whitepaper-11 仅 1 句话） | 内容不可读 | 第 5 章 |
| 4 | 全部条目无 difficulty / week / source 元数据 | 无法支撑学习路径联动 | 第 5 章 |
| 5 | 无进度追踪、无输出作业、无练习入口 | 学习闭环断档 | 第 6 章 |
| 6 | 单文件 data.js 承载全部内容，80 篇后体积不可控 | 维护与加载风险 | 第 7 章 |

### 1.2 建设目标：三大核心方向 + ▶ 量化指标

| 核心方向 | 建设内涵 | 落地载体 | ▶ 量化 KPI |
|----------|----------|----------|------------|
| 知识沉淀 | 建立「源文件 → 结构化 → 入站 → 持续更新」的知识生产流水线 | 内容入站 SOP、元数据规范、更新日志 | 19 份资产 100% 入站；每份资产可追溯到源文件 |
| 知识库 | 构建可导航、可检索、可追溯的知识组织结构 | 六大栏目、标签体系、全文搜索 | 站内约 80 篇文章；搜索命中率 ≥ 90%（标题+正文+标签） |
| 知识学习 | 提供有路径、有节奏、有输出、有验收的学习闭环 | 13 周成才路径、打卡、输出物验收、沙盘 | ▶ W13 完成率目标 ≥ 60%（打卡维度）；沙盘至少完成 1 个场景 |

### 1.3 目标人群与价值主张

| 人群 | 痛点 | 本站价值 |
|------|------|----------|
| 转型入行者（主） | 想学企业风险处置，资料零散、不知从何下手 | 3 个月成才路径 + 职业进阶地图（L1-L3）+ 全量方法论 |
| 在岗财务 / 法务 / 管理者 | 风控知识碎片化，学了无法立刻用于业务 | 「理论 → 模板 → 工具 → 沙盘」闭环，学了就能产出报告与方案 |
| 跨境物流 / 电商从业者（特色） | 行业特有风险缺乏适配方法 | 5 篇读书报告均含跨境物流/企业适配章节 |

### 1.4 参照模式

参照「跨境电商高级实战系列」学习网站的体系化课程模式：按「系列 → 模块 → 课时」三层组织；每模块配可下载工具与练习任务；栏目命名用行动语言。技术形态延续工作区已验证的纯静态学习站架构。

## 2 总体设计理念

### 2.1 三大支柱模型

网站由知识沉淀、知识库、知识学习三个支柱构成完整闭环：

- **知识沉淀层**：定义内容从何而来、如何清洗、如何结构化、如何更新，是全站的内容供给侧；
- **知识库层**：定义知识如何分类、组织、标注、关联、检索，是全站的内容承载侧；
- **知识学习层**：定义用户如何被引导、练习、输出、验收，是全站的能力转化侧。

### 2.2 设计原则

1. **路径为骨架**：学习路径是全站导航主线；
2. **理论为血肉**：方法论文档提供认知基础；
3. **工具为双手**：模板与测算工具可直接拿去做事；
4. **沙盘与案例为考场**：验证「学到什么、能处置什么」；
5. **内容与代码分离**：正文全部存于数据层，改内容不动代码；
6. **纯静态、零依赖、双击即用**：无需服务器与部署成本；
7. **▶ 渐进增强**：核心功能（阅读/导航/搜索）零门槛可用，进阶功能（打卡/沙盘/笔记）按需启用。

### 5.2 知识分类与标签体系

知识按「栏目 → 子板块 → 文章」三级组织；每篇文章挂三类标签：

- **难度标签**：入门 / 进阶 / 高阶，匹配学习阶段；
- **学习周标签**：对应 W0-W13，支撑路径页联动推荐；
- **主题标签**：处置手法（止损/谈判/重组/舆情/隔离）与行业（跨境/物流/电商/制造）。

### 5.5 内容入站生产流程

知识沉淀以「不篡改原文、只做结构化」为底线，按六步流水线执行：

1. **源文件清洗**：读取 docx/xlsx/pdf 原文，补全半截标题与截断正文，标注版本日期；
2. **章节化拆分**：长文按章节拆分，每篇独立成文（2000-8000 字为宜）；
3. **元数据补全**：按 5.3 规范补齐全部字段，维护元数据台账；
4. **▶ 摘要提取**：为每篇文章撰写 100 字内摘要，用于搜索命中预览与列表页展示；
5. **入站渲染**：按映射表分批写入对应数据文件，每入站一份即完成一次可验证的增量交付；
6. **校验上线**：核对标题完整、正文无缺口、链接与下载可用、标签与学习周匹配后发布。

### ▶ 5.6 内容编写规范

> 目的：保证 80 篇文章的结构一致性、质量底线与可维护性。

**5.6.1 章节化拆分粒度**

| 源文件类型 | 拆分策略 | 单篇字数参考 |
|------------|----------|--------------|
| 读书报告（8-10 万字总量级） | 每篇拆为 4 段：摘要 / 核心框架 / 章节拆解 / 企业适配 | 每段 2000-5000 字 |
| 白皮书（单章 5000-15000 字） | 按原章节拆分，24 条目合并为 7 章 | 每章 3000-8000 字 |
| 岗位方法论（单文件） | 按主题拆为 4 篇理论 + 5 张方法论卡 | 理论篇 3000-5000 字，方法卡 1500-3000 字 |
| 模板/工具 | 不拆分，每件套含：使用时机 + 结构拆解 + 填写指南 + 下载 | 每件套 1500-3000 字 |
| 法规 | 要点卡化处理，每条要点含：条文索引 + 白话解读 + 实务提示 | 每条 300-800 字 |

**5.6.2 HTML 标记规范**

```html
<!-- 文章正文统一使用以下标记 -->
<h2>章节标题</h2>           <!-- 文章内一级标题 -->
<h3>小节标题</h3>           <!-- 文章内二级标题 -->
<p>正文段落</p>              <!-- 所有正文段落必须用 <p> 包裹 -->
<ul> / <ol>                 <!-- 列表 -->
<blockquote>                <!-- 引用块 -->
<table>                     <!-- 表格（工具对比、矩阵等） -->
<strong>重点</strong>        <!-- 强调（不用 <b>） -->
<em>术语</em>               <!-- 术语首次出现（不用 <i>） -->
<!-- 禁止使用 -->
<!-- <div> 包裹正文 -->
<!-- 裸 <br> 代替 <p> -->
<!-- 内联 style -->
```

**5.6.3 字符串卫生**

- JS 字符串内禁裸双引号，中文语境用「」替代；
- 正文中的引号统一使用中文全角引号「」『』；
- 换行使用 `\n`，不使用实际换行符；
- 每篇文章的 contentHtml 字段值需通过 JS 字符串转义校验。

### 6.2 打卡与徽章机制

每周完成「阅读 → 工具使用 → 输出物」三步即打勾；筑基期（W1-W5）、进阶期（W6-W9）、成型期（W10-W13）全部打勾点亮对应阶段徽章。进度存 localStorage。

**▶ 质量保障机制**：
- 每步打勾前需回答 1 道自检题（从 6.1 自检清单中随机抽取），答对才算完成；
- 输出物打勾需上传文字描述（至少 50 字），说明本次输出物的核心结论；
- 连续 2 周未完成则触发「学习预警」提示，但不强制。

### 6.4 沙盘训练与案例库设计

**沙盘训练**：
- 基础 4 场景（客户拖欠/项目违约/债务集中到期/恶意扣货）：题干 → 输出要求 → 参考答案折叠；

## ▶ 7 技术支持方案

### 7.1 技术架构（优化版）

延续纯静态路线，**▶ 数据层按栏目分拆**，解决单文件瓶颈：

```
index.html          ← 入口壳（侧栏 + 主内容 + 脚本挂载）
style.css           ← 品牌变量、组件、移动端与打印样式
app.js              ← 导航/路由/搜索/进度/沙盘交互逻辑
data.js             ← ▶ 索引调度文件（站点元信息 + 栏目注册表）
data-path.js        ← ▶ 学习路径数据（13 周 + 打卡配置）
data-theory.js      ← ▶ 理论课堂数据（约 37 篇文章）
data-tools.js       ← ▶ 工具箱数据（8 件套 + 5 方法卡）
data-lab.js         ← ▶ 沙盘数据（5 场景）
data-cases.js       ← ▶ 案例库数据（17 案例）
data-law.js         ← ▶ 法规数据（2 组要点卡）
assets/             ← 模板与工具下载文件
```

**▶ 多文件架构设计要点**：

| 决策点 | 方案 | 理由 |
|--------|------|------|
| 加载方式 | index.html 按固定顺序 `<script>` 引入各数据文件 | file:// 双击可用，无 CORS 问题 |
| 数据注册 | data.js 定义 `SITE_DATA` 对象，各分文件通过 `SITE_DATA.theory = {...}` 挂载 | 保持单一全局变量，避免命名冲突 |
| 单文件体积 | 每个分文件控制在 200KB 以内 | 浏览器单文件解析无压力 |
| 按需加载 | 进入某栏目时再渲染对应数据（数据已全量加载，但 DOM 按需生成） | 首屏渲染性能 |
| 扩展性 | 新增栏目只需新增 data-xxx.js + 在 data.js 注册 | 低维护成本 |

### 7.3 ▶ 搜索架构设计

| 维度 | 方案 |
|------|------|
| 索引范围 | 标题 + tags + summary + contentHtml 前 500 字 |

### 7.4 实现避坑清单

| 序号 | 坑点 | 规避方案 |
|------|------|----------|
| 1 | 字符串卫生 | JS 字符串内禁裸双引号，中文用「」 |
| 2 | 长文渲染 | 正文用 contentHtml 直接存 HTML，绕开 Markdown 渲染器缺陷 |
| 3 | 缓存规避 | data 文件结构升级后改版本号强制刷新 |
| 4 | 兼容降级 | :has() 等新选择器提供降级方案 |
| 5 | 本地校验 | 开发期 `python -m http.server` 起本地服务 |
| 6 | 合规标注 | 白皮书标注出处；读书报告声明「个人学习整理」 |
| ▶ 7 | 数据文件加载顺序 | index.html 中 data.js 必须先于各分文件加载 |
| ▶ 8 | localStorage 容量监控 | 每次写入后检查用量，超过 4MB 时提示用户清理 |
| ▶ 9 | 多文件数据一致性 | 所有 id 全局唯一，构建时校验（可用简单脚本） |

| ▶ 内容风险 | 80 篇文章质量参差不齐 | 学习体验差 | P0.5 试跑校准规范；P1 分批校验；建立质量检查清单 |
| ▶ 工时风险 | 内容结构化工作量超预期 | 进度延期 | P0.5 获取真实速度后校准；P1 分 3 批交付，每批可独立验收 |

| ▶ 维护风险 | 单人维护 80 篇文章 | 更新停滞 | 数据文件分栏目拆分，每次只维护一个文件；入站 SOP 降低心智负担 |

## 12 结论与下一步建议

### 12.1 结论

本方案（v3）在 v2 基础上做了六项关键补强：

1. **量化验收**：每个核心方向配 KPI，每阶段有可量化验收标准；
2. **架构升级**：数据层从单文件拆分为多文件，解决 80 篇文章的体积与维护瓶颈；
3. **试跑机制**：P0 与 P1 之间插入 P0.5 试跑验证，获取真实速度后再批量推进；
4. **内容规范**：新增编写规范（拆分粒度、HTML 标记、字符串卫生），保证 80 篇文章质量一致；
5. **学习闭环**：打卡增加自检题、验收增加评分维度、进度支持导出备份；
6. **视觉具象**：核心页面线框描述，作为视觉确认的依据。

方案延续已验证的纯静态技术路线，建设成本低、阶段成果可验证、扩展路径清晰，具备直接进入实施的条件。
